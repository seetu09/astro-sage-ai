## 1. PROJECT OVERVIEW

**What it is.** AstroVeda is an AI-powered Vedic astrology web app: users generate Kundli (birth charts) with AI-written interpretations, read daily horoscopes, run Kundali matching (Ashtakoot Guna Milan), check doshas, get numerology and tarot readings, and chat with an "AI astrologer". Content is bilingual (English/Hindi). Money flows through Razorpay in two ways: wallet top-ups (which pay for AI chat questions) and one-off purchases that unlock the full paid Kundli report + PDF. There is also an "artifact store" (gemstones/rudraksha) whose catalog lives in Supabase, but whose checkout is not built yet.

**Stack** (from `package.json`, name `astroveda` v1.0.0):
- Framework: **Next.js 14.2.0** (App Router), **React 18.2**, **TypeScript 5**
- Styling: **Tailwind CSS 3.3** (+ `clsx`, `tailwind-merge`), **framer-motion**, **lucide-react**
- Data/auth: **@supabase/supabase-js 2.45**
- Payments: **Razorpay via direct REST calls** (no Razorpay SDK dependency); HMAC verification with Node `crypto`
- Rate limiting: **@upstash/ratelimit 2.1** + **@upstash/redis 1.39** with in-memory fallback
- AI: **Google Gemini** (`generativelanguage.googleapis.com`, called by raw `fetch` — no SDK dependency)
- PDF: **@react-pdf/renderer 4.9** (README's "Puppeteer" claim is stale)
- Validation/sanitization: **zod 4.6.5**, **isomorphic-dompurify 4.3**
- PWA: **next-pwa 5.6**; misc: `html2canvas`
- Dev/test: **vitest 1.6**, `eslint-config-next`, `typescript`, `autoprefixer`, `postcss`

**Deployment.** Vercel (`.vercel/repo.json` → project `astro-sage-ai`, directory `.`, origin `https://github.com/seetu09/astro-sage-ai`). Production origin hard-coded in SEO/meta as `https://astro-sage-ai.vercel.app`. ### 2.3 Authentication & session model

**End users (Supabase).** `lib/supabase.ts:5-19` lazily creates a browser client from `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` (throws if unset). `app/context/AuthContext.tsx` supports: `signInWithPassword` (:99), `signUp` (:114), `resetPasswordForEmail` (:130), **Google OAuth** via `supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: window.location.origin } })` (:143-146), phone OTP (`signInWithOtp` :157 / `verifyOtp` :168), and profile updates. Supabase-js defaults apply → session persisted in **browser localStorage** (no auth cookies). Server routes authenticate by **`Authorization: Bearer <access_token>`** validated with `supabase.auth.getUser(token)` (`lib/serverWallet.ts:36-54`) — used by `/api/wallet`, `/api/chat`, `/api/profile/reports`, `/api/payment/create-order|verify`.

**Admin (custom, shared secret).** `POST /api/admin/login` (`app/api/admin/login/route.ts:32-79`): rate-limited (MAX_ATTEMPTS/60s per IP), timing-safe compare (`safeEqual`) of the submitted password against `ADMIN_PASSWORD`, then sets cookie **`admin_session` = `ADMIN_SESSION_TOKEN`**, `httpOnly: true`, `secure` in production, `sameSite: 'lax'`, `path: '/'`, **`maxAge` 8 hours** (:70-76). `lib/adminSession.ts:26-34` `hasValidSession()` compares cookie to env var and **fails closed if the env var is unset**. `middleware.ts:36-59` gates `matcher: ['/admin/:path*', '/api/admin/:path*', '/debug-kundli/:path*']` — API paths get 401 JSON, pages redirect to `/admin/login?next=…`; public exceptions are exactly `/admin/login` and `/api/admin/login`. Defense in depth inside handlers: `api/admin/artifacts` GET/PUT re-check `hasValidSession` (:28, :46) and PUT additionally requires `x-admin-password` (:58); `api/admin/blogs` checks `ADMIN_PASSWORD` from the form body (:41) and otherwise **relies on the middleware** for the session gate.

**Third-party auth.** Google OAuth only (delegated to Supabase). No other identity providers.

**Cookies.** `admin_session` (8h, httpOnly/lax/secure-in-prod); `astroveda-language` (`lib/i18n/index.ts:39` — 1 year, `SameSite=Lax`, readable by JS, holds `en`/`hi`); no other first-party auth cookies. Supabase session = localStorage.

### 2.4 Payment / money path

**Integration:** Razorpay via plain HTTPS REST with Basic auth (`keyId:keySecret`) — no SDK in `package.json`.
- `POST /api/payment/create-order` (`route.ts:8-144`): rate limit 10/60s; ₹20 minimum; **`paymentType: 'wallet_topup'` requires sign-in** (:47-55), `'kundli_report'` allows anonymous purchase with chart metadata stuffed into Razorpay **order notes** (:105-114); returns `orderId/amount/currency/keyId`.
- `POST /api/payment/verify` (`route.ts:8-190`): rate limit 20/60s; HMAC-SHA256 signature check (`order_id|payment_id`, :43-52); **server-side order re-fetch** requiring `status === 'paid'` (:67-100); then (a) idempotent wallet credit for `wallet_topup` (:104-129), (b) `recordPurchasedKundliReport(...)` for `kundli_report` (:139-164), (c) mints `issueUnlockToken()` (:169).
- `POST /api/payment/validate` — re-validates a stored unlock token (HMAC + 30-day TTL) on AppContext mount.
- `POST /api/payment/reset` — by design a no-op acknowledgement (token is stateless; `route.ts:10-15`).

**Unlock token:** `lib/paymentUnlock.ts` — base64url(`{orderId,paymentId,iat}`) + HMAC; secret = `RAZORPAY_KEY_SECRET || PAYMENT_UNLOCK_SECRET` (:16). Enforced server-side in `/api/kundali/generate` (`x-unlock-token` header, :783-786) and `/api/kundali/pdf` (`route.ts:190` — token **or** ownership row).

**Wallet credits:** live in `wallet_balances`/`wallet_transactions` (001), written exclusively through service-role RPCs (`lib/serverWallet.ts:22-117`), debited per chat question (`consume_chat_credit`, 3 free then ₹5) with refund on AI failure. Client mirror `WalletContext` is explicitly a UX affordance only (`README:93`).

**Wired vs stubbed:**
- ✅ Wired: wallet top-up end-to-end; Kundli report purchase end-to-end (order → verify → ownership row → unlock token → full report + PDF); server-side paywall on generate/PDF; profile "Downloaded Reports".
- ❌ Stubbed/absent: **store/artifact checkout** (no `paymentType` for artifacts, buy button disabled); `payment/reset` is an ack-only endpoint by design; `api/matchmaking` unrelated to money.

## 10. RISKS

1. **Blog publishing is filesystem-bound and will fail in production.** `app/api/admin/blogs/route.ts:45-47` writes the cover image into `public/blogs/` and `:61` rewrites `data/posts.json`; Vercel's runtime FS is read-only — the exact failure migration `003` documents for artifacts (`supabase/migrations/003_artifact_catalog.sql:5-9`). *Trigger:* an admin publishes (or tries to publish) a post on the deployed site → 500, nothing persisted, image lost.
2. **A client component imports a service-role module, so email→account auto-binding silently never happens.** `app/components/UserProfileModal.tsx:141-147` does `await import("@/lib/serverPurchasedReports")` and calls `bindPurchasedKundliToUser()`; that module goes straight to `getServiceSupabase()` (`lib/serverPurchasedReports.ts:194`), which needs `SUPABASE_SERVICE_ROLE_KEY` — undefined in the browser — and the throw is swallowed by `catch { /* best-effort */ }`. *Trigger:* any signed-in user opening the profile modal → binding is a no-op forever (and server-only code is now in the client graph). The purchase list itself still loads because it goes through `/api/profile/reports` (`:148-150`).
3. **`kundali_charts` has no migration, is written with the anon key, and write errors are unchecked.** Reads/writes at `app/api/kundali/generate/route.ts:824-829` and `:848-863` use the **anon-key** client; the upsert's returned `{error}` is never inspected (only thrown exceptions are caught at `:864`). *Trigger A:* if the table's RLS insert policy is permissive (needed for anon upsert to work at all), **any unauthenticated visitor can write arbitrary rows** to the production database; *Trigger B:* if it's restrictive, the cache silently never populates and every request recomputes — invisible to ops because failures are logged at best.
4. **Idempotency check fails open toward double-crediting.** `lib/serverWallet.ts:130-132` `hasWalletCreditForPayment()` returns `false` on *any* thrown error, and `app/api/payment/verify/route.ts:104-118` credits the wallet when that returns falsy — so a transient Supabase read failure on a *repeat* verification of the same payment credits it again. *Trigger:* user re-submits verification while Supabase is flaky → wallet credited twice for one payment.
5. **Rate limiting silently degrades to per-instance memory.** `lib/rateLimit.ts:79-84` captures Upstash config at module load and `:121-123`/`:131-134` fall back to a local `Map`. *Trigger:* `UPSTASH_REDIS_REST_URL/TOKEN` unset in Vercel (status UNVERIFIED — `.env.example` ships them blank) or a Redis error → N concurrent lambdas each allow the full quota (e.g. `/api/chat` 5/min *per instance*, `/api/kundali/generate` similarly), so AI-spend protection is weaker than the code comments imply; failures are only `console.error`'d (`:132`).
6. **`next.config.js` externals/tracing keys are ignored on Next 14.2, risking PDF font failures.** `next.config.js:21` `serverExternalPackages` and `:22-31` `outputFileTracingIncludes` are Next-15-style keys (in 14.2 they must be `experimental.serverComponentsExternalPackages` / `experimental.outputFileTracingIncludes` — see `node_modules/next/dist/server/config-schema.js:207,272,279`; top-level `serverExternalPackages` appears nowhere in `next/dist`). *Trigger:* a production `/api/kundali/pdf` render needing pdfkit's `.afm`/`.cjs` assets that were never traced → "Cannot find module …Helvetica.cjs" at runtime, exactly the error the comment (`next.config.js:18-20`) tried to prevent.
7. **One 429 omits the standard `Retry-After` header.** `app/api/dosha-check/route.ts:98-101` returns `retryAfter` only in the JSON body while all 15+ sibling routes set the header. *Trigger:* a well-behaved client (or CDN) hitting the dosha-check limit gets no protocol-level back-off signal.

8. **`/api/artifacts?debug=1` is unauthenticated environment reconnaissance.** `app/api/artifacts/route.ts:34-65` returns booleans/lengths/prefix-shapes for `SUPABASE_URL`, the service key, and the anon key to **any caller** (values are withheld, but "serviceKeyStartsWithEyJ", lengths, whitespace/quote anomalies are not). *Trigger:* anyone requests the URL — useful to an attacker mapping config hygiene before probing other endpoints.
